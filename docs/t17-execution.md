日期：2026-10-11。沿用 T11 的 10 份合成 JD 和 T15 已保存的模型响应；本轮没有新的模型调用、真实简历或招聘网站输入。

## 判读规则

每个原子项独立记录 JD 原文片段、类别、T15 输出字段与精确文本。原文里的并列技术可以拆开，但一个模型输出**列表项整串**可对应多个原子项，例如 `jd02` 两项都指向“必备 MySQL 与 Redis”；`jd01` 则指向两个分别输出的列表项。原子标签若改写原文字面表达，须另写 `normalization_note` 供人工复核；脚本只能检验说明存在，不能证明改写语义正确。`required` 只用于明确必备或需要的条件，`preferred` 用于明确加分项，职责进入 `responsibilities`；教育、届别、岗位与地点分别映射到各自标量字段。`jd09` 中“请另议”的具体日期作为待确定信息，不当作已满足条件。

`jd08` 将 **MySQL 调优** 和 **PostgreSQL** 分为两个原子项，避免沿用旧金标中“二者都要求调优”的扩写。`jd04` 的“熟悉接口评审”另起分句，没有明确标注必备或加分；**T11 旧金标和 T15 模型输出都将它放入 `required`**，本轮重新审视原文后标为 `needs_review`，不强判对错。这是与旧金标的口径分歧，不能把旧金标当作独立裁决。无对应原文片段的模型词条不能从输出反向生成金标。

[人工映射](../tests/fixtures/t17_jd_atoms.json)同时绑定 T11 fixture 与 T15 原报告的 SHA-256。[离线校验脚本](../scripts/review_t17_jd_atoms.py)检查每个用例 ID、原文片段、模型输出原文、类别到字段的映射，以及待复核理由；还把未关联的 `required`、`preferred`、`responsibilities` 输出单列，供检查漏标或多余输出，不使用模糊相似度替人工裁决。
