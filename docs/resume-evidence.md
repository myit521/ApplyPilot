# 简历表达、技术证据与面试准备

更新：2026-09-30。求职定位是 Java 后端为主、Agent/AI 应用为辅。ApplyPilot 作为第二项目，展示把模型接入真实业务流程的工程判断；不为凑技术栈增加 Java 转发层、微服务或复杂 RAG。

## 1. 当前可诚实描述的范围

可写“开发了基于事实引用的简历生成原型，包含 JD 解析、事实检索、分段生成、人工审核中断和基础导出”。不能把这句话延伸为已完成稳定投递、自动恢复或零幻觉。

2026-09-29 全套 48 项测试通过是特定环境、主要模型替身下的测试结果，不是生产可靠性、真实模型效果或性能指标。当前缺陷见[审计](audit-2026-09-29.md)。

不使用旧上下文中的支持率、通过率、耗时提升等占位数字。没有数据集、分母、版本和复现记录的数字不进入简历。

## 2. 最值得建设的四个亮点

下列表述是**完成对应验收后才可采用的候选文案**，不是当前成果声明。

| 亮点 | 可用表述方向 | 解锁证据 | 对应任务 |
| --- | --- | --- | --- |
| 事实约束与可解释匹配 | 将个人经历建模为带修订和来源的事实，逐项关联职位要求；结合规则校验、语义复核和人工确认限制夸大表述 | 未确认事实不可用；数字/技能/贡献反例；标注集和失败样例 | T2、T4、T5、T11 |
| 人工审核与版本一致性 | 设计草稿修订和批准快照，以事务和唯一约束保证版本、引用与事件一致，支持重复请求安全重放 | 并发批准、写入失败、响应丢失重试；修改事实后历史不漂移 | T6、T7 |
| 可恢复的 AI 任务执行 | 基于持久化任务与 LangGraph checkpoint 实现有界重试、取消和中断恢复，区分业务状态与图状态 | 并发创建、进程重启、取消后模型返回、费用重复边界说明 | T8 |
| 投递追踪及有限浏览器辅助 | 绑定职位、批准版本和投递来源；后续通过用户确认的字段计划辅助填写，失败可回退人工 | 人工投递链路先完成；扩展仅在执行/回读/权限测试通过后写入 | T9；S3 可选 |

简历选 3–4 条即可，每条突出问题、设计和证据，避免只列 LangGraph、pgvector、Playwright。没有扩展证据时，第四条只写版本绑定和人工投递追踪。

## 3. MVP 完成后的项目简介模板

> ApplyPilot：面向校招的事实约束简历定制与投递追踪工具。基于 Python、FastAPI 和 PostgreSQL，组织职位匹配、简历改写、校验、人工批准和版本留痕，支持失败处理与人工接管。

这段只能在 MVP 真正验收后使用。是否加入 LangGraph 或 pgvector 取决于能否解释它的具体收益；向量没有优于关键词的证据就不把“混合检索提升效果”写成亮点。

涉及开源组件或参考代码应说明自己的贡献：领域数据模型、事实边界、一致性设计、测试、适配和交互改进。不要将第三方完整功能包装为独立开发。

## 4. 面试官可能追问

| 问题 | 必须能展示的回答或证据 |
| --- | --- |
| 为什么用户不用通用聊天机器人？ | 一个职位的要求→事实→草稿→批准→投递版本链路 |
| 事实库本身错误怎么办？ | 草稿/确认边界、来源等级、人工责任、停用与修订处理；不承诺自动证明真实 |
| 数字和技能怎么验证？ | 子串误判反例、单位/范围处理、技能等价策略和测试 |
| 语义模型误判或不可用怎么办？ | 明确待处理，人工核对；评测中的误拦/漏拦，不能只说“再问一次” |
| 为什么用 LangGraph，而不是函数调用？ | 人工中断和可持久化执行位置的收益；业务事务不依赖图状态 |
| checkpoint 为什么不等于恢复？ | 调度来源、未完成任务发现、幂等执行、重试和外部调用重复费用 |
| 审批过程中宕机怎么办？ | 事务内写入范围、唯一约束、响应丢失后的重放、图状态对账 |
| 用户改了事实，历史简历怎么办？ | 修订快照与停用策略；历史保留，新生成重新检查 |
| 幂等键怎么设计？ | 原子占位、请求摘要、同键异参冲突、并发测试 |
| 需要 pgvector 吗？ | 个人数据规模、关键词基线、Recall@5 和无证据样例；允许移除复杂度 |
| Java 岗位为何做 Python？ | 选用成熟模型工具交付功能，突出通用后端事务/任务/测试能力；不假装此项目验证了 Java 能力 |
| 填写成功怎么知道？ | 字段回读、部分失败、页面指纹；填写与提交分开，网站自动保存边界 |
| 如何确保不泄露简历和密钥？ | 数据流、日志脱敏、服务端密钥、扩展权限与配对；当前本机部署限制 |
| 有没有真实提升数据？ | 提供版本化评测和计时；没有就说明未测，不编造百分比 |
| 并发和规模有多大？ | 目前单用户单实例；展示实测而非虚构 QPS，解释何时需要队列与拆分 |

## 5. 证据包

每个亮点至少关联一个实现提交、一项能失败的回归测试、一个正常或失败演示和一段限制说明。评测按[验证手册](validation-and-demo.md)记录；公开材料只用脱敏/合成数据。

对简历的更新顺序是：实现 → 测试 → 演示 → 保存证据 → 修改表述。文档中出现设计图、状态机或接口草案，不能跳过前四步。
