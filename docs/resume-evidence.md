# 简历表达、技术证据与面试准备

更新：2026-10-23。代码验收基准：`dc475bf0543a1f968ddbab59f470773832f1823b`（T34）。求职定位为 Java 后端主项目、Agent/AI 应用第二项目。ApplyPilot 展示模型接入业务流程时的事务、状态、验证和人工责任边界，不为技术栈增加 Java 转发服务。

## 1. 可直接使用的简历条目

> ApplyPilot：基于 Python、FastAPI、PostgreSQL 和 LangGraph 的本机简历定制原型，围绕事实引用组织职位匹配、生成校验、人工审批、冻结版本导出与用户自行投递后的留痕。

简历按篇幅选用以下 3–4 条；每条都应能演示相应流程和失败反例。

- 将经历组织为带修订与来源的事实，关联职位要求和生成主张，结合规则校验、语义复核与人工确认约束简历改写，保留引用链供审核追溯。
- 在数据库事务内校验引用事实的当前修订并冻结审批快照，支持批准请求安全重放；新任务在入队事务中保存职位输入，复用通过当前门禁的 JD 解析，避免排队后职位修改导致输入漂移。
- 基于持久化任务与 LangGraph checkpoint 实现单实例中断恢复、有限重试和取消；通过脱敏调用日志关联任务、节点与尝试次数，区分供应商已报告用量和未知用量。
- 将用户手工填写的投递记录绑定批准版本，保留 `user_reported` 来源与 `unknown` 状态，支持从冻结内容导出 DOCX，并在页面流程中核对版本一致性。

| 条目 | 可展示的实现与证据 | 表述边界 |
| --- | --- | --- |

| 恢复与观测 | `src/applypilot/task_repo.py`、`src/applypilot/workflow.py`、`src/applypilot/model_usage.py`；[T30](t30-execution.md)、[T31](t31-execution.md)、[T32](t32-execution.md) | 单实例；日志尽力输出，不是持久化费用账本、配额或恰好一次执行 |

## 2. 当前证据能说明什么

最近一次完整回归记录为 **T34：399 passed、3 warnings，148.20 秒**，包含临时 PostgreSQL、备份恢复、任务恢复及未跳过的本机 Edge 浏览器流程。T34 由 DSH 只读复核两个投递页修复，主审运行完整测试；此前 T32 的 398 项仍保留为历史证据。耗时是该次测试时长，不是产品性能指标。旧 T10 的 217 项、T26 的 318 项仅是历史快照，不作为当前验收数。主功能草稿 PR #1（T6 起延续）仍未合并。

T32 使用默认 DeepSeekAdapter、真实本机 HTTP 服务、Edge 和临时 PostgreSQL，仅在供应商 HTTP 边界提供合成响应，嵌入使用 NullEmbeddingProvider。六次调用覆盖页面解析、初始生成/复核、人工退回生成/复核和编辑复核；五次合成 usage 为 reported，一次 missing 保持 null。批准、导出和手工留痕没有追加模型调用。它验证控制流、一致性和观测，不验证真实模型质量、真实计费、真实向量检索、招聘网站兼容或 DOCX 多页视觉效果。

该彩排还发现 T31 纯 UUID 单测漏掉真实任务 ID `wf_` 加 32 位十六进制串，导致日志丢失 run_id；T32 以生产格式回归复现并修复。这是“单测通过仍需串联真实接线”的具体面试案例，不能把 T31 当作此前已覆盖真实 ID 的证据。日志省略提示词、生成原文、密钥和原始响应，用量缺失也不按零成本处理。

[T27](t27-execution.md) 完成过 **一条合成资料的真实模型 API 案例**，使用限额演示适配器/临时工具，人工核对后批准，审核页只读渲染检查；它不是默认浏览器流程调用真实模型的全链验收，也不是产品默认适配器具备演示工具累计预算机制的证明。

[T25](t25-execution.md) 可展示 Java/JavaScript、SQL/PostgreSQL 的词法误命中修复，以及固定夹具、模型和权重后复跑的方法。混合 Recall@5=1.0 只适用于 8 条有相关事实的合成查询；无相关事实的查询仍返回向量候选，不能写成总体准确率或真实招聘效果提升。通常无需把该小样本数字放进简历。

## 3. 面试追问与应准备的回答

| 问题 | 必须能解释或展示的内容 |
| --- | --- |
| 为什么不直接用聊天机器人？ | 演示职位要求→事实引用→草稿修订→人工批准→冻结版本→用户留痕；说明状态和版本约束的价值 |
| 事实库错了，或模型仍然夸大怎么办？ | 草稿/确认边界、来源、修订与停用、数字/技能反例；人工负责最终核对，不承诺“零幻觉” |
| 为什么 checkpoint 不等于恰好一次？ | 外部模型请求已发生但 checkpoint 未落盘时，恢复可能重复调用；任务发现、幂等业务写入和外部收费是不同边界 |
| 审批时宕机或事实变化怎么办？ | 事务、唯一约束、修订冲突拒绝、响应丢失后的安全重放与图状态对账；展示冻结后不漂移 |
| 旧任务为何没有入队输入保证？ | 迁移保留 `job_snapshot=NULL`，不伪造历史；只对新预留任务声明入队快照，升级需停止旧 worker |
| token 上限是否就是费用预算？ | 输入为字符上限，输出有单次 max_tokens；重试、重启和新任务可继续消费，没有任务/账户持久化账本与总配额 |
| 没有 usage 是否说明免费？ | missing/invalid/unavailable 均未知；started 没有 finished 也可能已收费；日志可能丢失，不能简单相加宣称总费用 |
| 为什么单测没发现日志关联问题？ | T31 使用裸 UUID，仓库实际生成 wf_ ID；T32 默认适配器浏览器接线暴露缺口，再增加生产格式和非法前缀反例 |
| 为什么用 LangGraph、pgvector？ | 前者用于中断和持久化执行位置，业务事务独立；后者须对比关键词基线、固定标注和无证据查询，不能只报栈名 |
| 记录成功是否等于投递成功？ | 只是用户自述且绑定批准版本；展示 user_reported/unknown，DOCX 下载本身不创建投递记录 |
| Java 岗位为何做 Python 项目？ | 使用成熟模型工具交付流程，展示通用后端事务、任务和测试能力；Java 能力由主项目证明 |
| 并发、公开部署与真实收益呢？ | 当前本机单用户单实例；未验证多用户、公开部署、真实用户收益，不虚构 QPS、百分比或提效数据 |

## 4. 交付与公开材料

每条简历亮点准备一段实现位置、一项失败反例、一段正常/失败演示和限制说明。数字须有版本、分母和复现记录；第三方组件能力与自己的领域建模、事务、适配和测试贡献分开说明。

公开演示只使用合成/脱敏资料。真实模型质量、公开部署、多用户和许可证/第三方代码合规尚不能据上述记录宣称完成；既有公开 GitHub 旧对象或缓存是否彻底清除仍不明确，不把分支清理写成全历史隐私清除。现阶段不将浏览器扩展、自动投递、生产可靠性或费用保证列为已实现亮点。
