# T12 Delivery Baseline Implementation Plan

> **For agentic workers:** Use subagent-driven-development for independent container and CI slices, with a separate read-only review before integration. Steps use checkboxes for tracking.

**Goal:** Make the single-instance local app start predictably in a new environment, run a no-secret CI baseline, recover a copied database, and emit useful logs without personal content.

**Architecture:** A lean Python app image shares PostgreSQL with the existing Compose file; startup applies idempotent migrations before serving. CI covers non-integration tests on the validated Windows/Python platform. An explicit backup/restore drill targets a distinct database. Worker events log IDs, step, attempts, and error type only.

**Tech Stack:** Python 3.13, Docker Compose, PostgreSQL 16/pgvector, GitHub Actions, pytest.

**Spec:** [Roadmap T12](../../roadmap.md), [minimum observability and recovery](../../validation-and-demo.md).

## Global Constraints

- Local single user only; no public deployment or real application submission.
- No real model key or network model call in CI or smoke checks.
- Keep the existing database volume and migration history; no volume deletion to upgrade.
- Logs must not contain full JD, resume text, email, phone, connection strings, or API keys.
- A LICENSE cannot be invented without the maintainer's license choice.

## Review Focus

- Existing named DB volume must migrate on app restart, not only on first volume creation.
- Container readiness must reflect checkpoint and business schema, not merely an open TCP socket.
- Runtime dependencies must include every import required at startup but exclude testing and optional embedding packages.
- Backup success is insufficient: restore into a distinct database and query versions, citations, and applications.
- CI must explicitly state which integration scenarios require Docker and are not run there.

### Task 1: App container and local Compose

**Files:** `Dockerfile`, `requirements.runtime.txt`, `docker-compose.yml`.

- [ ] Build a Python 3.13 image containing `src` and `db` and a minimal pinned runtime dependency list.
- [ ] Add a localhost-bound app service that waits for a healthy DB, runs `python -m applypilot.db`, then starts Uvicorn.
- [ ] Verify `docker compose config`, image build, clean-volume start, `/health/live` and `/health/ready`, restart with existing data.

### Task 2: No-secret CI

**Files:** `.github/workflows/ci.yml`.

- [ ] Install the repository's Windows/Python 3.13 lock in CI and run `pytest -m "not integration"` without model secrets.
- [ ] Parse workflow YAML locally and document that Docker integration tests remain local verification.

### Task 3: Recoverable data and traceable errors

**Files:** `src/applypilot/task_worker.py`, focused tests, `docs/t12-execution.md`.

- [ ] Write failing tests for worker logs carrying run/job/attempt/error type while excluding exception text.
- [ ] Add minimal structured event fields; run focused and full tests.
- [ ] Backup a synthetic source DB and restore into a distinct DB; check schema version, approved versions, fact snapshots and application rows. Preserve both databases when the drill ends.
- [ ] Write a runbook for unavailable DB, model timeout, approval reconciliation, worker restart, and restore.

### Task 4: Delivery evidence

**Files:** `README.md`, `docs/roadmap.md`, `docs/validation-and-demo.md`, `docs/t12-execution.md`.

- [ ] Record exact build, smoke, migration, CI static check, test, and restore commands and results.
- [ ] Inventory current fixture licenses/origins and inspect tracked files/history for exposed personal data; record limitations without choosing a license for the owner.
- [ ] Obtain independent Agent review, commit and push only verified work.

## Self-review

The container, CI, backup drill, and logs are independent gates. If the image or restore cannot be verified locally, T12 remains partial and documentation must say so. The earlier 5h estimate is optimistic for a cold image build plus restore drill; evidence takes precedence over the schedule. The user has already authorized continued execution without a plan-confirmation pause.
