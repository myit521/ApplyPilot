# T8 持久化工作流任务设计

基准：`adcb223`。T7 的批准事务与不可变快照保持权威；T8 只解决创建工作流到等待人工批准之间的任务生命周期，以及进程重启后的继续执行。

## 问题与边界

当前 `POST /api/workflows` 在数据库占位前启动 daemon 线程。同一个幂等键可能对应不同职位，线程异常只写进程内字典，重启后没有待办扫描。单独新增任务表而不接入执行器会造成永久排队，因此对外启用必须等队列 worker 和恢复路径一起通过验收。

只支持单应用实例、一个有界 worker；不承诺多实例租约、模型调用恰好一次或自动投递。模型调用可能在崩溃后重放，业务写入必须以 T7 的唯一约束和幂等对账保护。人工批准仍由用户请求触发，不由 worker 代签。

## 数据权威与状态

新增 `workflow_tasks`，以 `run_id` 引用 `workflow_runs`，保存 `job_id`、全局唯一的可空 `idempotency_key`、状态、尝试次数、下次执行时间、取消请求、脱敏错误和时间戳。任务状态为 `queued`、`running`、`retry_wait`、`waiting_approval`、`completed`、`failed`、`cancelled`。`workflow_runs` 继续保存图状态供既有详情页读取；LangGraph checkpoint 只保存图进度，不替代任务状态或批准事务。

创建请求先在同一数据库事务中写入 `workflow_runs` 和 `workflow_tasks`，提交后才唤醒 worker。同键同职位在任何任务状态返回原 run；同键异职位返回 409。没有键时每次创建新 run。不能安全证明职位归属的旧 `wf_<key>` 记录须返回冲突，不能误认作新请求。幂等键不因失败或取消而复用；用户想新跑一次要提供新键。

单 worker 领取到期任务；启动时扫描并重新入队上次进程遗留的 `running`。执行前检查取消请求，执行后根据 checkpoint 分别落为等待批准或完成。可重试的模型限流/超时使用固定上限与退避；不可重试错误和耗尽次数持久化为失败。人工取消不杀正在运行的模型调用，但调用返回后禁止继续写入后续业务状态。审批事务与取消的先后由同 run 锁明确串行化；已批准的版本不能被取消回滚。

## 风险与验证

- 崩溃点：占位前、占位提交后、图 checkpoint 写入前后、等待批准后，逐点重启验证任务可继续或明确失败。
- 并发同键：必须只有一条任务和一条 run；异职位 409。
- 恢复可能重放模型调用，严禁宣称 exactly-once；批准记录和冻结版本只能有一份。
- 取消与模型返回竞争：返回后不应继续生成下一步；已批准的事务保持不可变。
- 错误响应和日志不含 JD、简历正文、密钥或原始模型输出。

## 切片顺序

1. 数据库迁移与原子占位仓库，独立测试，不改变现有 API 行为。
2. API 入队与单 worker 联动，同时移除先启动线程路径；此切片结束才暴露新语义。
3. 重启恢复、有限重试、取消和状态查询；验证 T7 批准对账与无重复冻结。
