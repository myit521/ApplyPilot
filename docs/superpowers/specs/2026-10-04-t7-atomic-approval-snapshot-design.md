# T7 原子批准与不可变快照设计

状态：待用户审阅。基线：`0996276`。对应路线：`docs/roadmap.md` 的 T7。

## 目标

当用户批准一个已通过校验的草稿时，系统应持久保存一个完整、可核对且不可变的批准数据包。批准版本、简历主张、事实来源快照和审计事件必须一起提交；重复请求只能返回同一个结果；LangGraph checkpoint 与业务数据库状态不一致时，系统必须能识别并重试对账。

用户看到的结果是：批准响应中的版本 ID 和内容哈希指向一份固定简历；网络超时后重复提交不会创建第二个版本；后续修改或停用事实不会改变已批准数据包中的内容和来源依据。

## 当前问题

当前 `POST /api/workflows/{run_id}/approve` 先恢复 LangGraph 中断并推进至 `READY_TO_APPLY`，然后调用 `_freeze_version()` 写入 `resume_versions` 和 `resume_claims`。`db.connect()` 使用 autocommit，两个步骤之间没有共同事务；版本和多条主张插入也没有显式事务。主张写入失败时可能留下不完整版本。请求成功但响应丢失时，工作流已离开 approval 节点，重试会先得到 409，无法返回原版本。当前版本仅保存职位 ID、分区文案和事实 ID，未冻结职位与事实修订的来源快照，也没有批准审计事件。

## 决策

### 权威数据来源

PostgreSQL 是批准结果、版本内容、引用快照与批准审计事件的权威来源。LangGraph 只记录生成流程的位置；它的 checkpoint 不与业务事务假装原子。系统先提交 PostgreSQL 批准数据包，再推进图状态；checkpoint 更新失败时保留明确的待对账状态，并由相同批准请求触发重试。

### 单一批准数据包

新增 `workflow_approvals` 表作为幂等记录：`run_id` 主键并引用 `workflow_runs`，保存 `draft_revision`、`content_sha256`、唯一的 `version_id`、`graph_reconciled` 和批准时间。一个 run 最多一条批准记录，版本通过该表与工作流关联；不要求旧 `resume_versions` 行回填 run ID。`resume_versions.content` 保存带 `schema_version` 的分区简历和职位快照；引用事实正文只保存在版本事实快照表，避免重复存储。规范哈希从版本 content 与关联事实快照组合计算。批准数据包包含：

- 已批准的分区简历及每条主张的文本、事实 ID 和匹配要求；
- 批准时的职位快照，至少包含职位 ID、公司、职位名、来源、URL、原始 JD 和解析结果；
- 每个被引用事实的 ID、修订号及 `fact_revisions.snapshot` 中的不可变来源内容。

保留现有 `resume_claims` 作为可查询的主张表。新增 `resume_version_facts` 表，以 `(version_id, fact_id)` 为主键，保存 `fact_revision` 和不可变 `snapshot` JSONB，并通过 `(fact_id, fact_revision)` 外键引用 `fact_revisions`。历史版本不依赖事实当前行来重建内容。既有版本保持可读，迁移不补造 run ID 或快照。新表与 `workflow_approvals` 是唯一新增的业务表；版本与幂等元数据集中在批准记录，不向 `resume_versions` 冗余添加 run 字段。

### 内容哈希

哈希作用于完整的批准数据包，而不是数据库自增 ID、提交时间或 checkpoint。使用有显式版本号的规范 JSON：UTF-8 编码、对象键排序、紧凑分隔符、非 ASCII 字符原样编码；随后计算 SHA-256 十六进制摘要。包中包含 schema/version 标记、草稿修订、职位快照、按稳定键排序的事实快照和有序分区主张。哈希算法和包结构版本一旦发布不得静默改变；之后格式升级须带新版本标记。

### 幂等与并发

批准幂等键由 `(run_id, draft_revision)` 构成，并由唯一约束保护。批准入口在检查 checkpoint 状态之前先查持久批准记录：若 run 与修订相同且是批准请求，重试返回原 `version_id` 与哈希；若修订不同或该 run 已有不兼容决定，返回 409。相同请求不得再插版本、主张、快照或审计事件。

同一 run 的编辑与批准操作使用 PostgreSQL advisory lock 串行化，锁覆盖 checkpoint 读取、修订比较、必要的事实验证及 checkpoint 更新，避免编辑和批准并发时冻结过期正文。批准事务锁定被引用事实的当前行，验证事实仍启用、已确认且修订号与工作流检索快照相同；然后读取对应不可变事实修订快照。事实写入不能在校验和快照读取之间穿过批准事务。

### 提交与 checkpoint 对账流程

1. 按 run 获取串行化锁，读取批准数据包是否已存在。存在时按幂等规则核对并直接进入对账。
2. 不存在时读取 checkpoint，要求它等待 approval，且 `expected_revision` 等于当前草稿修订；批准只能针对已通过 T5 校验的草稿。
3. 在一个 PostgreSQL 事务中锁定并验证职位、被引用事实及其修订；构建并哈希完整数据包；插入批准关联、已批准版本、全部主张、全部事实快照和一个批准审计事件。任一步失败则事务全部回滚。
4. 事务提交后恢复 LangGraph。若图已显示批准完成，记录 `graph_reconciled=true`；若推进失败，保留数据库批准事实并标记待对账，不删除版本或审计事件。
5. 待对账请求返回可识别的 202 状态和同一版本 ID；重复同一审批请求会重试 checkpoint 对账。查询工作流时优先反映持久化批准记录，不能把数据库已批准、checkpoint 未对账的状态显示为仍可编辑或可再次批准。

事务内插入使用同一个 psycopg connection 和显式 `conn.transaction()`。唯一约束冲突后的处理必须读取既有记录并按修订规则返回，不能把所有数据库错误都误报为幂等成功。

### API 与导出

- 批准成功响应返回 `resume_version_id`、`draft_revision`、`content_sha256` 和状态。
- 同修订重试返回完全相同的版本 ID、修订号和哈希。
- 过期修订、run 决定冲突或事实在批准前改变返回 409，不写入任何批准数据。
- 事务中途失败返回错误，且数据库不得残留版本、主张、快照或批准事件。
- checkpoint 失败发生在事务提交后时返回 202 并标记 `APPROVAL_RECONCILIATION_PENDING`；此状态不能被当作可继续编辑的审批中状态。
- DOCX 导出从批准版本中的职位与简历快照读取数据，不因职位或事实后续变化而漂移。

拒绝意见、人工编辑和通过校验的规则继续使用 T6 行为；拒绝操作不生成批准版本。本任务不提供事实修改后的自动批准或旧版本重写。

## 数据库变更

新增版本化 SQL migration，不重写旧 migration。迁移创建 `workflow_approvals` 和 `resume_version_facts`，并添加所需主键、唯一约束、外键和检查约束；不修改旧行。版本快照、主张和审计记录通过外键关联；已有版本和投递记录保留原 ID、内容和关联。审计事件包含 run ID、草稿修订、版本 ID、哈希和引用事实数量，不写入 API 密钥或完整职位正文的额外副本。运行就绪检查必须确认新 migration 已应用。

部署迁移可重复执行，现有版本保留原状。新版本必须使用新契约；旧版本允许关联字段为空。具体列名、外键和索引须在实施计划中与当前 schema/test fixture 核对后确定。

## 失败状态与用户可恢复行为

| 失败点 | 持久结果 | 用户重试行为 |
| --- | --- | --- |
| 事实或修订检查失败 | 无版本、快照或批准事件 | 返回 409，用户创建新工作流或重新生成 |
| 任一快照/主张/事件写入失败 | PostgreSQL 事务回滚，无批准数据 | 显示可重试错误；再次提交重新执行 |
| 事务已提交，HTTP 响应丢失 | 完整批准包已存在，图可能尚未对账 | 相同 run/修订返回原版本并尝试对账 |
| checkpoint 推进失败 | 完整批准包存在，待对账 | 状态明确为对账待处理；重试只推进图，不重复写版本 |
| 并发相同批准 | 一个批准包提交 | 两个请求最终看到同一版本和哈希 |
| 并发不同修订或与编辑竞争 | 锁与修订检查决定唯一顺序 | 旧修订收到 409，不产生第二个版本 |
| 批准后事实被编辑或停用 | 批准数据包中的快照不变 | 原版本仍可导出并核对旧修订 |

## 验收标准

1. 一个数据库事务完整保存批准版本、全部主张、所有被引用事实修订快照、批准记录和唯一审计事件。
2. 任一子写入失败都会回滚整个批准数据包，不留下孤立版本或不完整引用。
3. 同 run、同草稿修订的重复请求返回原版本与哈希；同 run 不接受不兼容的第二个批准修订。
4. 草稿过期、事实修订改变、事实被停用或未确认时拒绝批准，且零批准写入。
5. 并发批准只能产生一个版本；编辑与批准通过相同 run 锁串行化。
6. PostgreSQL 提交后模拟 checkpoint 失败，API 和查询能显示“已批准、待对账”；同请求重试恢复 checkpoint，不创建重复记录。
7. 修改事实或职位后，旧版本 JSON、来源快照、哈希和 DOCX 内容保持一致。
8. 迁移可在已有 T1–T6 schema 上运行，旧简历版本和投递关系不变；重复迁移无副作用。

## 测试策略

- PostgreSQL 集成测试：事务回滚、迁移兼容、唯一约束和事实行锁；不可只用 mock 数据库证明事务原子性。
- API 集成测试：同修订重放、过期修订、事实变化、批准拒绝、响应丢失后的重试。
- 并发测试：两个批准请求竞争；编辑请求与批准请求竞争；校验唯一版本、单条批准事件和一致哈希。
- 故障注入：在每个子插入点抛错并确认零残留；在数据库提交后令 `graph.invoke` 失败，再重试验证对账。
- 快照回归：批准后更新事实、停用事实、修改职位记录；核对保存快照和导出字节/内容不变。
- 全量现有测试及不依赖 Docker 的纯单元测试均通过。

## 非目标

- 不重构或替换 LangGraph checkpoint，不声称 PostgreSQL 事务能涵盖 checkpoint。
- 不实现持久化 worker、进程重启自动扫描或租约机制；这些属于 T8。T7 的恢复触发点是重复审批请求和可见的待对账状态。
- 不实现应用投递、浏览器扩展、网站提交或用户认证。
- 不添加通用事件平台、消息队列或多服务架构。
- 不将拒绝事件、所有用户操作或完整模型输入纳入本阶段的审计体系。

## 主要审查风险

1. HTTP 成功响应丢失后，图状态已前进：API 必须先读持久批准记录，再检查 graph 是否等待审批。
2. 多个并发请求使用不同 psycopg 连接：事务、唯一约束和 run 锁必须在真实 PostgreSQL 上验证。
3. 事实修订验证和来源快照读取之间发生更新：批准事务必须锁当前事实行并引用不可变修订快照。
4. checkpoint 恢复成功后、对账标记写入前进程退出：重试必须识别图已批准，不得二次推进或复制业务数据。
5. 旧版本和 DOCX 依赖旧字段：迁移不能要求旧行伪造 run/哈希，导出需兼容旧版本并优先使用新版本冻结快照。
